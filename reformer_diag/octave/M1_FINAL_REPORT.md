# M1 baseline: final report (native Octave cross-check of the SSMR benchmark)

Generated by `reformer_diag/octave/build_report.py` from files on disk; checked by `verify_report.py`. Simulation only. Octave is not MATLAB. Scope: Modes 1 and 2, np = 50, the README case studies and the paper Section 5.1 ethanol step. Nothing has been sent to anyone.

## Bottom line

1. **Native MATLAB reference obtained** (MATLAB 26.1.0.3346988 (R2026a) Update 5, MATLAB Online): the released author script was run for STEP, CS1, CS2T and CS2P with only the README case settings changed in copies (plus one inserted line applying the ethanol step in the open-loop STEP case). Against it, the Python port's largest H2 difference is 0.0564% of nominal and its largest IAE difference 0.141%: every approved equivalence gate passes for all four cases (section 2a).
2. CS1 reproduces the paper: MATLAB IAE 7.9461e-05 mol (-0.05% vs published), Python +0.09%.
3. CS2T and CS2P do NOT reproduce the paper's IAE, and the authors' own code in MATLAB misses by the same amount (-10.52% and -9.30%). The discrepancy is between the released code and the paper, not in the port. For CS2T it equals one extra 0.1-min sample of startup error to within 0.03% (section 5, post-hoc).
4. Reproducibility pitfall found: control.m keeps PID state in persistent variables that SSMR_simulation.m's `clear` does not reset; running cases back to back in one MATLAB session changed CS1's IAE by +20.12% vs published. `clear control` fixes it.
5. The paper's 'time constant 0.25 min' is not what a first-order-plus-dead-time fit returns (about 0.05 min); the elapsed time from the input step to 63.2% of the rise is about 0.25 min (section 6). The frozen time-constant gate stays failed.
6. Octave cannot integrate the Mode 2 steam startup (NonNegative is ignored by Octave ode15s; section 4). In Mode 1, Octave agrees with Python on CS1 (max dH2 0.12% of nominal) but STEP narrowly FAILS the 0.5% gate (0.566%, in the two steepest rows; section 3).
7. M1 status: equivalence CLOSED (native MATLAB). Paper gates: CS1 PASS; CS2T, CS2P and the STEP time constant FAIL, attributed to the code-vs-paper definitions, pending the two author questions (AUTHOR_QUESTIONS_DRAFT.md, not sent).

## 3. Where STEP differs

Rows with |dH2| > 0.05% of nominal (Octave vs Python): t = 2.1 min (0.566%), t = 2.2 min (0.346%). All other rows: max 0.0222%.
The two Octave runs (this lane vs the other lane, both Octave 6.4) differ from each other by up to 0.549% at t = 2.1 min.
Cause: upstream records H2 as the global F_H2 left by the LAST right-hand-side call ode15s made in the interval, not the value at the interval end point. In the steepest 0.1 min of the rise that number depends on the solver's step path, so implementations differ there by about half a percent. The frozen gate is kept; this is reported as a narrow FAIL with its cause.

## 4. Mode 2 in Octave: why it could not be run

- Neither installed Octave ode15s.m (6.4.0, 11.3.0) contains any NonNegative handling (text search of both files); the author script's `'NonNegative', 1:8*2*np` is silently ignored. MATLAB honours it.
- Untouched script: interval 1 of 101 took 293 s (Octave 6.4) and 617 s (Octave 11.3); interval 2 did not finish in over 25 min of awake time. Upstream RHS costs 0.11 s per call in Octave; each default Jacobian needs 800 calls.
- Supplied-Jacobian and NonNegative-emulation variants fail in interval 2 (ethanol first enters the steam-filled reactor) with IDA "corrector convergence failed repeatedly or with |h| = hmin"; failure times are in the run table.
- The Python port also needed a documented positivity extension to pass this startup (other lane, `NUMERICAL_EXTENSION_PROTOCOL.md`). No non-MATLAB solver tried so far integrates this startup as released.
- Consequence: Octave cannot serve as the Mode 2 native reference; native MATLAB does (section 2a).

| CS2P (CS2P_extended) | 2.2494e-04 | 2.48e-04 | 2.3057e-05 | 2.7638e-05 | 0.834 | +1.85% |

CS2T and CS2P start from the steam-only state, where H2 is zero and the error equals the full set-point. One extra 0.1-min sample of that error, as a time basis starting one sample earlier or an integration to 10.1 min would add, closes the CS2T gap almost exactly. CS1 starts at steady state, so the same extra sample adds almost nothing, consistent with its near-zero gap. CS2P is closed less well. This pattern was found after seeing results; it is a question for the first author, not a passed gate.

## 6. The "time constant 0.25 min"

- FOPDT fit (frozen method) on the Python dense trace: tau 0.0505 min, dead time 0.2035 min; gate vs 0.25 min: FAIL_DYNAMICS_REFERENCE_AMBIGUITY (unchanged).
- Elapsed time from the input step (t = 2 min) to 63.2% of the rise, Python dense trace (column `hydrogen_mol_min`): 0.2612 min.
- Upstream control.m sets `tao = 0.25` and uses the classical Ziegler-Nichols ultimate-cycle formulas (Kp = 0.6 Ku, Ki = 1.2 Ku/Pu, Kd = 3 Ku Pu/40, then detuned), where that value plays the role of the ultimate period.
- Reading: the paper may mean elapsed time to 63.2% including dead time. Post-hoc; question for the author.
